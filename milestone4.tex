\section{Summary of Progress}

Since Milestone 3, we extended our stereo SAD implementation from a single-GPU CUDA
program to a distributed MPI+CUDA version. The new version splits the input image by
rows across MPI ranks, assigns each rank to a GPU, runs the tiled SAD kernel on each
local image slab, and gathers the final disparity map back to rank~0.

The main additions are a \texttt{main\_mpi.cu}, which handles the MPI driver logic and a script for running the scaling experiments. We kept the GPU kernels from Milestone 3
unchanged, and the MPI driver currently uses the tiled kernel because it was the
fastest version from our earlier benchmarks.

We tested the distributed version on 1, 2, and 4 ranks for two image sizes. In all
cases, the gathered disparity map matched the CPU reference on the synthetic stereo
pair. We also collected strong-scaling results on a four-GPU node. In addition, we added support for loading real stereo image pairs from
PGM files, which lets us run the same pipeline on standard stereo datasets instead
of only synthetic images.

We haven't done object tracking yet, so that is one feature of the final project that we still have to implement for the final
report.

\section{Distributed Algorithm and Data Decomposition}

We use a simple 1-D row decomposition. If the image has height $H$ and we run with
$P$ MPI ranks, each rank gets roughly $H/P$ rows. Rank~$i$ owns rows
$[r_i, r_i + h_i)$, where
\[
h_i = \lfloor H/P \rfloor + [i < H \bmod P].
\]
This keeps the work balanced even when the image height is not exactly divisible by
the number of ranks.

The SAD kernel needs a square patch around each output pixel, so rows near the edge
of a rank's local slab depend on neighboring rows. To handle this, each rank includes
a small halo of \texttt{radius} rows above and below its owned region. For now, we use
a full-image broadcast instead of a point-to-point halo exchange. This means every
rank receives the whole left and right image, then locally extracts the rows it needs,
including halo rows. Only the owned rows are gathered back to rank~0.

This is not the most communication-efficient approach, but it keeps the MPI logic
simple and was reasonable for the image sizes we tested. A better version for larger
images would use \texttt{MPI\_Scatterv} to send each rank only its needed rows, plus
\texttt{MPI\_Sendrecv} to exchange halo rows with neighboring ranks.

We also considered a 2-D decomposition, but it does not help as much for this kernel.
The disparity search is horizontal, and each output pixel already searches along the
row direction. Splitting columns would make the horizontal search window harder to
handle. Because of that, row partitioning is the cleaner choice for this milestone.

\section{MPI Implementation}

The MPI implementation uses two main collective operations. First, rank~0 creates or
loads the stereo image pair and broadcasts the image data to all ranks with
\texttt{MPI\_Bcast}. Each rank then extracts its local slab and copies it to its GPU.
After the CUDA kernel finishes, each rank copies its local disparity slab back to the
host, and \texttt{MPI\_Gatherv} collects the slabs into the full output disparity map
on rank~0.

We use \texttt{MPI\_Gatherv} instead of \texttt{MPI\_Gather} because different ranks
can own slightly different numbers of rows when $H$ is not divisible by $P$. The
send counts and displacements are computed from the row partitioning.

There is currently no overlap between communication and computation. The broadcast
finishes before the CUDA kernel starts, and the gather starts only after all ranks
finish their GPU work. This makes the implementation easier to reason about, but it
also means communication overhead is exposed directly in the timing. In the final
version, it would be better to overlap communication with computation, especially for
streaming frames.

The current version also stages MPI transfers through host memory. We do not use
CUDA-aware MPI. For the sizes tested here, this was a reasonable tradeoff because the
images are small, and the added complexity of direct GPU-buffer communication was not
worth it yet.

\section{CUDA Integration}

Each MPI rank selects a GPU using
\[
\texttt{cudaSetDevice(rank \% num\_devices)}.
\]
On the four-GPU node, this assigns ranks 0--3 to four separate GPUs.

The existing \texttt{GpuBuffers} wrapper from Milestone 3 is reused. The only
difference is that each rank now allocates buffers for its local slab rather than the
full image. This means memory use per GPU decreases as we add ranks.

No changes were needed inside the CUDA kernels. Each kernel already accepts an image
with arbitrary height and handles border pixels internally. For MPI, this works out
nicely because the halo rows can be passed into the kernel as part of the local slab,
and then discarded before the gather.

For timing, the CUDA kernel still uses CUDA events. In the MPI driver, we also use
\texttt{MPI\_Wtime} around the broadcast, kernel call, and gather. Since distributed
runtime is limited by the slowest rank, we report the maximum kernel time across ranks
using \texttt{MPI\_Reduce} with \texttt{MPI\_MAX}.

\section{Real Stereo Image Support}
\label{sec:realimages}

Until this milestone, our tests used a synthetic stereo pair. The left image was a
sinusoidal pattern, and the right image was generated by shifting the left image by a
known constant disparity. This was useful for correctness testing because the true
disparity was known everywhere, but it is not representative of real stereo data.

We added a \texttt{load\_pgm} function that reads 8-bit binary PGM images. The parser
handles the P5 header, skips comment lines, checks that \texttt{maxval = 255}, and
loads the binary pixel data into the existing \texttt{Image} format. This keeps the
image-loading code simple and avoids adding another image library dependency.

Both \texttt{main\_gpu} and \texttt{main\_mpi} now support
\texttt{-{}-left PATH} and \texttt{-{}-right PATH}. When these flags are provided,
the program loads the stereo pair from disk instead of generating a synthetic pair.
The image width and height are taken from the PGM header, so the command-line height
and width are ignored. Since we do not currently load a ground-truth disparity file,
the accuracy printout is skipped for real images.

In the MPI version, rank~0 loads the image dimensions and pixel data, broadcasts the
dimensions first, and then broadcasts the image buffers. After that, the rest of the
pipeline is the same as for synthetic images: row decomposition, halo extraction,
CUDA kernel launch, and \texttt{MPI\_Gatherv}.

For future testing, the most useful datasets are Middlebury, KITTI, and ETH3D. These
datasets provide rectified stereo pairs, which match the horizontal-disparity
assumption used by our SAD implementation. Middlebury is useful for high-resolution
indoor scenes, KITTI is more representative of outdoor robotic perception, and ETH3D
has accurate ground truth at moderate image sizes.

\section{Correctness Testing}

We tested the distributed implementation against the CPU reference using the same
synthetic stereo setup as Milestone 3. The true disparity was fixed at
$d^* = 24$, with $D_{\max}=64$ and patch radius $R=2$.

We ran the tests on two image sizes, $480 \times 640$ and $960 \times 1280$, using
1, 2, and 4 MPI ranks. In all cases, the final gathered disparity map had
\[
\text{MAE} = 0.000 \text{ px}
\]
and a bad-pixel rate of
\[
0.00\%.
\]
This confirms that the row partitioning and halo handling are correct. In particular,
the gather does not drop or duplicate rows, and the kernel's border handling works
both at the true image boundary and at local slab boundaries.

\section{Performance, Scaling, and Profiling}

We benchmarked the MPI+CUDA version on a single node, \texttt{hpcc-gpu-5-1}, with
four Quadro RTX~6000 GPUs. We used SLURM with \texttt{-{}-gres gpu:4} and
\texttt{-{}-ntasks=4}. Each rank was assigned to a separate GPU. All timings are
averaged over 10 repeats.

\subsection{Computation vs. Communication}

The larger image scales much better than the smaller one. For the $960\times1280$
case, going from 1 to 4 ranks improves wall time from 21.67 ms to 6.90 ms, giving a
$3.14\times$ speedup and 78.5\% efficiency. The kernel time itself scales almost
ideally, dropping from 1.749 ms to 0.464 ms. This suggests that the CUDA work is
being split evenly across GPUs and that there is no major load imbalance.

The main reason scaling is not perfectly linear is communication. The full input
image is broadcast to every rank, and the final disparity image is gathered back to
rank~0. These communication costs do not shrink as quickly as the per-rank compute
work. As more ranks are added, each GPU gets fewer rows to process, but the full-image
broadcast and final gather are still present.

This effect is more noticeable for the $480\times640$ case. With 4 ranks, the wall
time improves from 5.79 ms to 2.96 ms, which is only a $1.95\times$ speedup. Each
rank only processes 120 rows, so the kernel is already very short. At that point,
MPI overhead and host-device transfer overhead become a much larger fraction of the
total runtime.

\subsection{Parallel Efficiency}

The 4-rank efficiency is 78.5\% for the larger image, but only 49\% for the smaller
image. This is the expected trend for strong scaling: when the problem size is fixed,
adding more GPUs reduces the compute work per GPU, but the fixed overheads remain.

For the large image, each rank still has enough work to keep the GPU useful, so the
parallel efficiency stays fairly high. For the small image, each local slab is too
small, and the overhead of launching kernels, transferring data, and running MPI
collectives starts to dominate. This means the smaller image is below the crossover
point where using four GPUs is clearly worth it.

\section{Discussion of Bottlenecks}

The biggest bottleneck in the current distributed version is the full-image
\texttt{MPI\_Bcast}. This is simple, but it sends more data than necessary. Each rank
only needs its own rows plus a small halo, so a future version should use
\texttt{MPI\_Scatterv} and explicitly exchange halo rows with neighboring ranks. That
would reduce the amount of data sent to each rank and should improve scaling,
especially for larger images or more GPUs.

Another bottleneck is host-device transfer. The current code copies each rank's slab
from host to GPU before the kernel, and copies the disparity slab back after the
kernel. For a real-time perception pipeline, these copies would matter even more
because there would typically be one kernel launch per frame. A better version would
use pinned memory and \texttt{cudaMemcpyAsync}, and ideally overlap transfers with
computation using CUDA streams.

There is also no communication-computation overlap yet. The current pipeline is
sequential: broadcast, copy to GPU, run kernel, copy back, gather. This is fine for a
milestone implementation, but a production version should pipeline frames so that the
next frame can be transferred or communicated while the current frame is computing.

Finally, the small-image results show that splitting work across too many GPUs can
hurt efficiency. With 4 ranks on the $480\times640$ image, each GPU only receives 120
rows. That is not enough work to fully amortize the fixed overheads. This suggests
that multi-GPU scaling is most useful for larger images, larger disparity ranges, or
more expensive stereo kernels.

\paragraph{Optimizations with the largest impact.}
The single biggest improvement in this milestone was the tiled SAD kernel inherited
from Milestone 3. In Milestone 3, the tiled version was already the fastest variant,
and we carried it forward unchanged because it fit naturally into the per-slab
decomposition. The row partitioning itself also helped almost linearly on the kernel:
for the $960\times1280$ image, the CUDA kernel time dropped from 1.749\,ms at 1 rank
to 0.464\,ms at 4 ranks ($3.8\times$ speedup, close to ideal $4\times$). The choice
of 1-D row decomposition over a 2-D block decomposition was also important for
correctness simplicity: horizontal disparity search depends on full rows, so row
ownership maps cleanly onto the SAD computation with only a narrow halo. Had we used a
2-D block layout, each block would have needed both row and column halo exchanges,
adding complexity without a corresponding performance benefit for this kernel.

\paragraph{Expected scaling ceiling.}
The current implementation is expected to stop scaling effectively beyond roughly
4--8 ranks for these image sizes. The \texttt{MPI\_Bcast} sends the full image
($H \times W$ bytes) to every rank regardless of how many ranks there are, so its
cost is $O(HW)$ and does not decrease as $P$ grows. The per-rank kernel work is
$O(HW/P)$, so the compute time halves with each doubling of rank count while
communication stays roughly fixed. At 4 ranks on the $960\times1280$ image,
communication (2.96\,ms) already exceeds kernel time (0.464\,ms) by a factor of
$6\times$. Doubling to 8 ranks would halve the kernel to $\approx0.23$\,ms while
broadcast cost remains near 3\,ms, making the wall time communication-bound and
yielding near-zero additional speedup. Replacing \texttt{MPI\_Bcast} with
\texttt{MPI\_Scatterv} plus halo exchange would reduce the per-rank communication
to $O(HW/P)$ plus a small $O(W \cdot R)$ halo term, which would shift the
scaling ceiling substantially higher.

\section{Challenges and Next Steps}

The main challenge for this milestone was integrating CUDA and MPI cleanly in the
build system. The MPI compiler wrapper produced flags that \texttt{nvcc} did not
accept, so we had to separate the CUDA compilation step from the MPI linking step.
After that, the actual MPI logic was relatively straightforward.

For the final report, our main next step is to replace the full-image broadcast with
\texttt{MPI\_Scatterv} plus explicit halo exchange. We also want to profile the MPI
version with Nsight Systems so we can confirm where time is being spent across MPI,
host-device transfers, and CUDA kernels. We also plan to test larger images and
larger disparity ranges, since those are the cases where the multi-GPU version should
benefit the most.

We also want to run the pipeline on real Middlebury or KITTI stereo pairs using the
new PGM loader. Since those images have more realistic texture, occlusion, and
lighting variation, they will be a better test of disparity quality than the
synthetic sinusoidal images. If time permits, we may still add a simple object
tracking stage, but the current priority is to finish the distributed stereo pipeline
and evaluate its scaling carefully.
